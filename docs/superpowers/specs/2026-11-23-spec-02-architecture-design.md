# SPEC 02: arquitectura de cuentas, respaldos y catálogo global

## Contexto y alcance

El propietario confirmó que SPEC 01 está terminada. SPEC 02 conserva IndexedDB como fuente local de entrenamientos y añade cuentas opcionales, respaldos remotos, un catálogo global para invitados y usuarios, y administración privada. La aplicación personal sigue siendo Android; la web se limita a administración. El catálogo y los respaldos tienen ciclos de sincronización independientes.

El código existente proporciona el contrato portable en `src/db/contractBackup.ts`, una revisión local capturada junto con la instantánea y 74 ejercicios Sinful Shell con identificadores estables en `src/domains/routine/data/sinfulShellCatalog.ts`. El serializador actual incluye salud y copias locales del catálogo: no se puede subir directamente sin aplicar la política de consentimiento y distinguir los datos globales reconstruibles de las personalizaciones personales.

## Límites y seguridad

- La API TypeScript y el panel administrativo se ejecutan en Vercel; PostgreSQL y la autenticación administrada se mantienen en Neon. Los secretos y las comprobaciones de roles permanecen en el servidor. Cada operación privada deriva el usuario de una sesión validada, nunca de un ID proporcionado por el cliente.
- Antes de seleccionar el mecanismo definitivo de sesión Android, se debe demostrar que el proveedor permite al trabajador nativo autenticarse y renovar la sesión sin WebView, con credenciales protegidas y revocación. No se supone que la cookie del WebView esté disponible para WorkManager. Los registros se restringen mediante invitaciones verificadas en el servidor.
- Las funciones Vercel tienen un límite predeterminado de 4.5 MB para el cuerpo. Las imágenes y respaldos potencialmente mayores se transfieren directamente a almacenamiento de objetos privado mediante autorizaciones breves y acotadas; el servidor valida propiedad, tamaño y hash antes de confirmar. La API no acepta una ruta de objeto arbitraria como prueba de propiedad. Fuente: https://vercel.com/docs/functions/limitations
- Los recursos privados no comparten rutas ni permisos con las imágenes públicas del catálogo. Se aplican límites de tamaño y frecuencia, validación estricta y auditoría de acciones administrativas. No se usa información personal en registros de diagnóstico.

## Respaldos y restauración

Cada instantánea se captura con una revisión local consistente y un manifiesto versionado y determinista. Salud se excluye salvo consentimiento explícito; las credenciales, cachés y el catálogo global se excluyen siempre. Las recetas, referencias históricas y personalizaciones personales permanecen incluidas. La preparación debe verificar que todas las mutaciones personales relevantes incrementan la revisión antes de usarla como indicador de cambios.

El cliente prepara una instantánea persistente mediante Capacitor; Kotlin no consulta Dexie. Las revisiones no preparadas permanecen señaladas hasta una preparación posterior con el WebView disponible. WorkManager envía únicamente instantáneas nativas ya preparadas, con conectividad, trabajo único y reintentos; una comprobación periódica tiene objetivo de 72 horas sin promesa de ejecución exacta. El respaldo manual es independiente del intervalo. La cuenta debe autorizar el primer respaldo tras vincularse.

La instantánea nativa pendiente se conserva cifrada con AES-GCM y clave de Android Keystore dentro de `noBackupFilesDir`, no en preferencias ni en el respaldo automático del sistema. El archivo se reemplaza mediante escritura temporal sincronizada y renombre atómico; se limita su tamaño y se comprueba autenticidad al leer. Cada instantánea incluye propietario, revisión y contenido. Tras una confirmación, solo se puede eliminar si siguen coincidiendo propietario, revisión y huella del contenido: una instantánea nueva nunca se elimina por completar un envío anterior. Si el archivo no se puede autenticar, se conserva y se informa error; no se marca como enviado. La clave real, el puente de Capacitor, el serializador completo y WorkManager requieren pruebas de integración e instrumentadas adicionales.

El trabajador debe mantener fijo el ID del sobre entre reintentos, respetar el ID y estado devueltos por preparación y solicitar un token vigente para cada operación privada. Ante una subida que pudo haberse completado antes de interrumpirse, no debe reemplazar un objeto ni asumir que una respuesta fallida demuestra su integridad: la reserva y confirmación del servidor deben verificar el manifiesto y cada componente existente antes de reconocer la copia. El código HTTP exacto de una repetición en Blob y la recuperación de objetos parcialmente cargados deben probarse con almacenamiento real antes de activar reintentos automáticos. Un conflicto de versión, identidad distinta, sesión caducada, error o resultado ambiguo conserva la copia local y comunica el estado; nunca se convierte en éxito ficticio.

En el almacén privado de desarrollo, una segunda carga con la misma URL y sin sobrescritura devolvió HTTP 400. Ese código no prueba por sí solo que el objeto exista ni sea correcto: ante él, el transporte solo puede continuar hacia las comprobaciones de reserva o confirmación del servidor, que validan las huellas reales. La recuperación de interrupciones completas sigue requiriendo pruebas integradas.

El servidor confirma solo después de verificar los objetos, hash y contrato; una clave idempotente y una restricción de unicidad evitan duplicados. La confirmación registra la revisión efectivamente enviada, sin borrar cambios posteriores. Un control de versión del respaldo base detecta divergencias entre dispositivos. En una transacción se publica la nueva versión antes de seleccionar las versiones antiguas que excedan cinco; la limpieza de objetos debe tolerar fallos y no eliminar objetos referenciados.

Antes de firmar cargas de imágenes personales, el servidor debe verificar el manifiesto subido y registrar de manera atómica la lista exacta de componentes y sus tamaños reservados. La suma de los tamaños declarados más el manifiesto debe coincidir con el tamaño total del respaldo y quedar por debajo de un límite configurado por el servidor. La clave de cada componente se deriva del hash de su identificador y su huella procede del manifiesto validado. El perfil y el respaldo pendiente se comprueban bajo bloqueo, con consentimiento de salud vigente. Los reintentos idénticos son idempotentes; tamaños, recursos o huellas diferentes son conflicto. Esto limita el espacio que una cuenta puede autorizar aunque cada URL individual tenga su propio límite. La confirmación todavía verifica bytes y huellas reales antes de hacer visible una versión.

Retención: al confirmar, mantener las cinco versiones confirmadas más recientes y transferir los identificadores de versiones excedentes a una cola duradera de limpieza de objetos en la misma transacción. Una clave base de una versión eliminada se vuelve nula sin alterar el propietario, y una operación pendiente basada en ella debe detectar conflicto contra la versión confirmada actual. Los objetos se eliminan únicamente después de la confirmación y del vencimiento de las URL temporales; la limpieza debe ser reintentable y comprobar de nuevo que ninguna versión conservada referencia los objetos. Los tiempos de confirmación usan el reloj al ejecutar la sentencia, ya que `now()` representa el comienzo de la transacción y puede ordenar incorrectamente dos confirmaciones concurrentes que esperan un bloqueo. Hasta implementar y probar la limpieza real, la cola no debe habilitarse en producción.

La preparación y la limpieza serializan por propietario mediante un bloqueo consultivo transaccional. El limpiador bloquea el elemento vencido, verifica que no exista un respaldo con ese propietario e identificador, enumera solo el prefijo derivado por servidor y elimina lotes acotados. Mantiene el elemento en cola al fallar o si quedan objetos; únicamente lo retira cuando el prefijo está vacío mientras conserva el bloqueo. Así un respaldo nuevo no puede reutilizar ese identificador durante una limpieza todavía en curso. Las llamadas al almacenamiento llevan timeout; la limpieza de cargas pendientes abandonadas requiere un mecanismo adicional.

Las versiones que permanecen pendientes durante siete días pueden retirarse de los metadatos y pasar a la misma cola de limpieza, con el mismo retraso antes de borrar objetos. La selección se vuelve a comprobar bajo los bloqueos del propietario; nunca se retiran versiones confirmadas por este proceso. El cliente debe conservar su instantánea local hasta obtener confirmación y preparar un nuevo identificador si la carga caduca.

La autorización de cada URL temporal mantiene el bloqueo consultivo y el bloqueo del perfil hasta terminar de firmar. Esto serializa la firma con la confirmación y la limpieza: ninguna solicitud que haya comprobado una versión antigua puede emitir un enlace nuevo después de que esa versión se haya retirado y limpiado. La llamada de firma tiene timeout y el vencimiento del enlace se calcula antes de contactar el proveedor.

La restauración presenta fecha, tamaño, versión y resumen, comprueba integridad y compatibilidad, detecta divergencia con datos locales y requiere una decisión explícita. La validación completa precede al reemplazo transaccional; ante cualquier fallo se conservan los datos locales. No se eliminan los flujos existentes de exportación hasta verificar respaldo y restauración remotos.

`GET /api/v1/sync/status` entrega a la cuenta autenticada la última versión confirmada, el número de cargas remotas pendientes y el consentimiento de salud del servidor. No afirma conocer cambios no preparados en el teléfono: el cliente debe compararlos con su revisión local. La consulta deriva propietario de la sesión, excluye manifiestos y enlaces y devuelve datos solo tras comprobar el perfil.

## Catálogo global

PostgreSQL conserva cada ID global inmutable, borradores, publicación, archivo y registro versionado de cambios. La publicación verifica autorización, datos e imágenes y actualiza versión y auditoría en la misma transacción. La API pública solo expone información publicada; los cambios de archivo permiten retirar opciones sin destruir referencias antiguas.

Una copia local versionada arranca con el catálogo incluido y se actualiza independientemente de las cuentas. Al abrir, volver al primer plano, recuperar conexión o entrar al catálogo se consulta la versión con limitación de frecuencia. Un conjunto validado se aplica completo en una transacción y solo entonces se confirma su versión. Las imágenes descargadas necesitan persistencia y verificación propias, con recurso alternativo; una descarga incompleta no reemplaza la última copia válida. Los cambios globales no modifican recetas personales ni instantáneas históricas.

Decisión de implementación: guardar la instantánea remota y su versión juntas en un registro de `localMetadata`, tabla interna ya existente y excluida de los respaldos personales. Esto evita cambiar la versión Dexie 8 y rechazar respaldos locales existentes por un cambio exclusivo de caché. Las imágenes se guardan en Cache Storage bajo su hash, separadas del caché del shell. El service worker no intercepta `/api` y solo elimina versiones antiguas del shell.

Una copia personal de un ejercicio global conserva en el campo existente `assetKind` una referencia versionada con SHA-256, tamaño y tipo de imagen; no incorpora los bytes globales al respaldo personal. Esa referencia se propaga a las recetas y snapshots históricos y permite recuperar de la caché la imagen verificada. Un valor desconocido o una imagen ausente utiliza la imagen de respaldo existente. En un dispositivo nuevo, la imagen se recupera cuando se descargue el catálogo que la contenga; recuperar imágenes de versiones archivadas requiere que el servicio remoto conserve y ofrezca esos recursos, todavía pendiente.

## Administración y comprobaciones

## Acceso Android y aspecto

La pantalla de cuenta se integra en la app móvil existente, respeta el ancho de 430 px y los controles accesibles y parte de la identidad oscura de ARSEN. Una composición viva en morado, jerarquía clara y texto en español presentan el correo, contraseña, acción de acceso y opción de continuar como invitado. Campos con etiquetas, autocompletado apropiado, foco visible y estados de carga y error evitan bloquear el entrenamiento local. La contraseña se mantiene solo durante el intento; no se registra ni almacena. El usuario pidió introducir sus credenciales dentro de ARSEN; si Clerk requiere una verificación adicional que la interfaz aún no cubre, se ofrecerá completar el acceso en el portal oficial, sin declarar autenticada una sesión incompleta.

El puente de Capacitor entrega al WebView solo estado e identidad mínima, nunca tokens ni secretos. Clerk permanece dueño de la sesión y de su renovación en Android. Un acceso exitoso no activa por sí solo respaldos ni sobrescribe datos: la autorización inicial y la resolución de conflictos son pasos posteriores. En navegador o sin configuración nativa se mantiene modo invitado con explicación explícita.

Las rutas administrativas comprueban sesión y rol en el servidor, incluidas las operaciones sobre objetos. El panel distingue guardar borrador de publicar y confirma disponibilidad remota, no recepción por dispositivos. Los metadatos de respaldo se separan de su contenido; el acceso sensible requiere autorización y auditoría. Las eliminaciones necesitan confirmación y protegen el último respaldo válido.

Los borradores administrativos se consultan con paginación acotada y se guardan con control optimista: el primer guardado exige que el ID no exista y las ediciones comparan el borrador que se abrió, para no sobrescribir cambios ajenos. Un guardado solo modifica `draft`; una entrada de auditoría con actor, acción e ID se escribe en la misma sentencia. El esquema del borrador acepta campos opcionales acotados, pero la publicación sigue exigiendo el contrato completo y la imagen verificada. La migración de auditoría de catálogo se prueba en PostgreSQL aislado y no se aplica a Neon hasta verificar el despliegue.

Archivar un ejercicio publicado es una única operación transaccional autorizada para administradores que marca el registro archivado, incrementa la versión global y guarda la acción y el actor; cualquier fallo revierte los tres cambios. Un ejercicio ausente o sin publicación no se archiva, y repetir el archivo ya realizado se informa como conflicto. Restaurarlo exige una publicación validada mediante la operación de publicación existente, de modo que nunca se vuelve visible una imagen no comprobada.

Para publicar imágenes, el verificador admite únicamente el origen HTTPS exacto configurado de un almacén público de Vercel Blob; rechaza otros dominios, credenciales y redirecciones. Consume el flujo con límite y timeout, exige tipo y tamaño declarados, comprueba la firma inicial del formato y compara SHA-256 antes de publicar. La comprobación de firma no equivale a una decodificación completa de la imagen. Si la verificación falla o expira, la publicación no ocurre. Esta restricción es independiente de los respaldos privados.

La carga de una imagen global requiere administrador y un token de almacén público distinto del token de respaldos. El servidor genera un nombre aleatorio inmutable dentro de `catalog/images/`, emite una autorización breve para un único archivo con tipo y tamaño limitados y devuelve su URL pública; nunca acepta una ruta enviada por el cliente. La imagen no pasa a ser parte del catálogo hasta que se guarda y publica un borrador y el servidor verifica sus bytes. La URL firmada no lleva el token general de almacenamiento y la ruta permanece deshabilitada sin la configuración completa y límites distribuidos.

La lista administrativa de cuentas devuelve únicamente metadatos necesarios para diagnóstico: ID, rol, fecha de alta, número de dispositivos, número de respaldos confirmados y fecha del último. No devuelve correo, manifiestos, imágenes, tokens ni datos de entrenamientos; el correo y más detalles de usuario requieren integración explícita y segura con Clerk. La consulta está paginada y solo se ejecuta tras verificar sesión y rol en servidor.

El detalle administrativo de respaldos acepta un identificador de cuenta y muestra solo las cinco versiones confirmadas conservadas: ID, dispositivo, revisión, versión de contrato, tamaño, fecha e inclusión de salud. No entrega el contenido, hashes ni URLs de descarga y no afirma que una copia esté verificada sin haber comprobado sus bytes. Una cuenta inexistente y una cuenta sin copias devuelven la misma lista vacía.

El panel será una aplicación web separada para escritorio y móvil, con la identidad oscura y morada de ARSEN. Clerk administra el acceso web; el navegador solicita un token nuevo para cada operación y no lo guarda en almacenamiento persistente. Los controles muestran únicamente datos y acciones que el servidor realmente proporciona. Los errores de sesión, rol, configuración o red se muestran claramente; no hay estadísticas inventadas ni acciones de respaldo que no existan. Un panel solo de diagnóstico y edición de catálogo sigue siendo parcial hasta implementar imágenes, usuarios y diagnósticos restantes.

La preparación de una invitación administrativa registra, en la misma sentencia que crea el registro local, el identificador del administrador, la acción `invitation.requested`, el UUID de la invitación y la fecha, sin correo ni token. Un reintento con el mismo UUID no duplica la auditoría. El registro significa que se solicitó la invitación, no que el proveedor haya entregado el mensaje. Si la auditoría falla se revierte la creación local y no se llama a Clerk.

Para iniciar el entorno de desarrollo con la cuenta de prueba creada por el propietario, el aprovisionamiento inicial exige una única cuenta en Clerk Development con sesión activa y correo principal verificado, y una base Neon sin perfiles. Una transacción toma un bloqueo de exclusión, vuelve a comprobar que no hay perfiles y crea exactamente ese perfil con rol administrador. Si existen varias cuentas, perfiles o una sesión no válida, no asigna roles automáticamente. Esta operación no se utiliza para altas posteriores ni para producción.

Las pruebas deben cubrir aislamiento entre usuarios, invitados sin permisos, integridad y rollback, divergencia, duplicados, consentimiento de salud, ejecución nativa sin WebView, errores transitorios, múltiples instalaciones y actualizaciones de catálogo interrumpidas. Las pruebas instrumentadas y la verificación en dispositivos reales complementan las pruebas locales; las restricciones de Android impiden garantizar horarios exactos o ejecución tras detención forzada.

## Decisiones que requieren validación técnica

La compatibilidad de Neon Managed Better Auth con renovación de sesión nativa, el proveedor y los límites concretos de almacenamiento de objetos, y la ejecución efectiva de WorkManager deben demostrarse en un entorno configurado antes de considerar entregada la solución. No se presupone que las cuotas gratuitas basten para cualquier número de usuarios o tamaño de respaldos.

La documentación de Neon indica que Managed Better Auth permite registros abiertos por defecto y que las restricciones integradas están pendientes: https://github.com/neondatabase/website/blob/main/content/docs/auth/authentication-flow.md. La activación de perfiles ARSEN mediante invitación protege los recursos de la aplicación, pero por sí sola no restringe la creación de cuentas en Neon. La SPEC exige restringir registros, así que esta incompatibilidad sigue abierta y debe resolverse antes de poner el sistema en producción.

Evaluación solicitada por el propietario: Clerk documenta un modo exclusivo por invitación (https://clerk.com/docs/guides/secure/restricting-access) y un SDK Android con `Clerk.auth.getToken()` (https://clerk.com/docs/android/reference/native-mobile/auth). Sus tokens de sesión son de corta duración y deben renovarse; aún no se ha demostrado que el SDK pueda rehidratar una sesión y obtener un token dentro de WorkManager tras terminar el proceso, sin abrir el WebView. Los claims predeterminados documentados no incluyen `aud` (https://clerk.com/docs/guides/sessions/session-tokens), por lo que el verificador actual que exige audiencia no debe conectarse sin definir y probar un contrato adecuado para Clerk. Si se adopta Clerk, la clave foránea a `neon_auth.user` y el canje local de invitaciones deben rediseñarse: Neon seguirá siendo PostgreSQL, pero no será la fuente de identidad. La evaluación no equivale a una integración funcional ni a una decisión de despliegue.

Clerk documenta inicialización en la clase `Application` (https://clerk.com/docs/android/reference/native-mobile/configuration) y requiere Android API 24 o superior (https://clerk.com/docs/android/getting-started/quickstart); el proyecto declara API mínima 26. Esto respalda la viabilidad de inicialización nativa, pero no demuestra por sí solo la renovación de sesión durante un trabajo en segundo plano ni tras un reinicio del proceso.

Para continuar con Clerk, los perfiles guardan su identificador externo sin una clave foránea a Neon Auth. La creación de perfiles sigue restringida a código de servidor; el canje local existente solo puede recibir correo e identidad obtenidos y verificados por el proveedor desde el servidor, nunca desde el cuerpo de una solicitud. Este canje no sustituye el modo de registro exclusivo por invitación de Clerk. Las migraciones iniciales 001–004 se aplicaron en Neon de desarrollo tras comprobar que la base estaba vacía y verificar su reversión. Antes de exponer rutas, deben verificarse el token y la sesión activa del proveedor y bloquearse por defecto ante errores.

La verificación específica de Clerk valida JWT RS256 con emisor, expiración, `nbf`, sujeto y `sid`; cuando existe `azp` debe estar en la lista permitida. Un token sin `azp` solo se permite mediante configuración explícita para clientes nativos. Después consulta la sesión del Backend API y exige identificador, usuario y estado activo coincidentes; una sesión revocada, pendiente o un fallo del proveedor deniega acceso. Fuentes: https://clerk.com/docs/guides/sessions/manual-jwt-verification y https://clerk.com/docs/reference/backend/sessions/get-session. No publicar hasta comprobar la configuración real y la semántica de renovación nativa.

Para el código de invitaciones local se ha elegido una validez inicial de siete días, tokens aleatorios de 32 bytes y almacenamiento exclusivo de su SHA-256. El canje compara el correo verificado obtenido por el servidor del proveedor y consume la invitación junto con la creación del perfil; aún debe conectarse al proveedor, probarse con conexiones concurrentes reales en Neon y resolverse cómo se relaciona con la invitación de Clerk sin exigir al usuario dos flujos independientes.

Clerk documenta que los metadatos públicos asignados por el servidor a una invitación pasan al usuario cuando acepta el enlace: https://clerk.com/docs/reference/backend/invitations/create-invitation. Es una posible forma de asociar una invitación de Clerk con una de ARSEN sin pedir dos enlaces; debe diseñarse y probarse el manejo de reintentos, caducidad y fallos entre Clerk y PostgreSQL antes de usarla. Los metadatos públicos son legibles por el usuario y no deben tratarse como secretos.

La asociación propuesta utiliza únicamente el UUID no secreto de la invitación local en metadatos públicos fijados por el servidor de Clerk. En la activación, el servidor vuelve a consultar directamente el usuario en Clerk, comprueba la sesión y el correo principal verificado, y canjea una invitación no expirada con el mismo UUID y correo en una única sentencia. El identificador por sí solo no autoriza una cuenta. Sigue pendiente la creación coordinada de la invitación en ambos servicios y la recuperación ante respuesta incierta; hasta entonces no se publica este flujo.
